# Deployment guide

Target setup: **Supabase** (PostgreSQL) + **Render** or **Railway** (API) + **Vercel** (frontend).
These steps are written from the project's configuration; I could not deploy to your accounts, so follow them once and run the
smoke test at the end. Provider dashboards change, so check each provider's current docs where a menu name differs.

## 1. Database (Supabase)
1. Create a project and note the database password.
2. Copy a Postgres connection string from the project's database settings. Prefer the **pooler** connection if your API host only
   supports IPv4 (Render does). Use `postgresql://...` form; the app accepts `postgres://` too.
3. Optional: run `backend/app/database/schema.sql` in the SQL editor. Otherwise the API creates the same tables on first start.
4. **Run `backend/app/database/supabase_hardening.sql`** in the SQL editor. It enables row level security with no policies so Supabase's
   auto-generated REST API cannot read your tables (the API connects directly as the `postgres` role, which is unaffected).
   Run it again after any new table is added.

## 2. API (Render, using the repo's `Dockerfile`)
1. Push the repository to GitHub.
2. In Render: New > Blueprint, pick the repo (it reads `render.yaml`), or create a Web Service with Runtime = Docker and the repo root as context.
3. Set environment variables: `DATABASE_URL` (from step 1), `CORS_ORIGINS` (your Vercel URL, set after step 3 and then redeploy),
   `JWT_SECRET` (generated by the blueprint, or `python -c "import secrets; print(secrets.token_urlsafe(48))"`).
4. Health check path: `/api/health`.
5. The container starts uvicorn with `--proxy-headers --forwarded-allow-ips='*'`. Keep these: without them every visitor looks like the
   proxy's IP and shares one rate-limit bucket.

**Railway:** New Project > Deploy from GitHub repo. Railway detects the root `Dockerfile`. Add the same variables. Keep the repo root as the build context
so `data/` is included (a service root directory of `backend/` would exclude it and the API would fail to find its datasets).

Free tiers may sleep when idle, so the first request after a pause can take a while.

## 3. Frontend (Vercel)
1. Import the repo. Set **Root Directory** to `frontend`; framework preset Vite (build `npm run build`, output `dist`).
2. Add `VITE_API_URL` = your API's public URL (no trailing slash). It is baked in at build time, so redeploy after changing it.
3. `frontend/vercel.json` rewrites all paths to `index.html` so deep links like `/dashboard` work.
4. Add the Vercel URL to the API's `CORS_ORIGINS` and redeploy the API.

## 4. Verify
```bash
python scripts/smoke_test.py https://YOUR-API-URL
```
All 16 steps should print PASS. Then open the Vercel site, register, finish onboarding and click through each page.

## Optional: enable the LLM for CareerAI
Set `LLM_API_BASE` (an OpenAI-compatible base URL), `LLM_API_KEY` and `LLM_MODEL` on the API service only. Chat replies then show the
"AI model" badge; on any provider error the built-in assistant answers instead. Check a few replies for quality before relying on it.

## Production checklist
- [ ] `JWT_SECRET` is random and only set on the server
- [ ] `CORS_ORIGINS` lists only your real frontend origin(s)
- [ ] Supabase hardening script has been run
- [ ] Smoke test passes against the deployed API
- [ ] Decide on token storage (httpOnly cookie) and add Redis-backed rate limiting before heavy traffic
- [ ] Add Alembic migrations before the first schema change
- [ ] Back up the database (Supabase backups or scheduled `pg_dump`)
